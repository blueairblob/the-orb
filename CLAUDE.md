# CLAUDE.md — working brief for The Orb

This file orients an AI assistant (e.g. Claude Code on the dev host) to the project. Read it,
then read `docs/PRD.md`. The PRD is authoritative; if this file and the PRD ever disagree, the
PRD wins and this file should be corrected.

## What this project is

The Orb is an audio-first AI Dungeon Master. The deliverable that matters is the **engine**, not
the demo game. The engine is a **harness** that takes an unbounded LLM and makes it behave as a
consistent character inside hard, deterministic rules.

## The current situation (read before doing anything)

- The design is **complete**. Do **not** propose new features or expand scope. If a new problem
  appears, the right instinct is almost always "that's just state again" (PRD §22).
- **Nothing has been built.** The repo is a scaffold plus the PRD.
- The single blocking unknown is **the spike** (PRD §0, `spike/README.md`). Until it passes,
  building the full engine is premature.

## Non-negotiable architecture (do not violate these)

1. **The engine is the director; the AI is the actor.** Deterministic code owns dice, HP,
   inventory, rules, positions, NPC mood/memory. The LLM owns only narration, tone, and character
   voice. Never let the model write to world state directly. (PRD §3)
2. **Everything is an object; the AI narrates their state.** The object model is the spine — the
   brief handed to the model each turn is *auto-generated by walking the object graph*, never
   hand-written. Rigour in the object model = a cleaner prompt that keeps a small model on rails.
   (PRD §4)
3. **Reality is permanent.** The road stays where it is; the trees do not disappear. Pin
   everything solid in the engine; let the AI paint only on top. (PRD §3)
4. **The less you say, the more confident you appear** (the Yoda principle). Sparse, deliberate
   lines. This is character *and* it solves latency, battery, and TTS quality at once. (PRD §3)
5. **Improvised detail becomes canon instantly.** The moment the AI invents something, the engine
   writes it to state and feeds it back forever. Spontaneous once per detail, bound thereafter.
   (PRD §22, Gotcha #3)

## Build order (PRD §11, §24)

- **Phase 1 — Python desktop engine, first.** Object model, state machine, brief-builder, and the
  smallest possible voice loop (one cell, one guard). This is the hard part and where the engine
  gets *designed*. Prove the heartbeat: you speak → engine decides → it speaks back.
- **Phase 2 — the phone shell, later.** React Native or similar. Do not let phone concerns
  contaminate Phase 1. *The engine is portable; the shell is disposable. Build them in that order.*
- **Evennia (PRD §11):** evaluate early (half a day) — does borrowing its typeclass world model
  and LLM-NPC contrib save months, or drag in a MUD server you'll spend months removing? Structural
  decision; make it before building the object model from scratch.

## The model

- **Gemma 4 E2B**, quantised, `.litertlm` format — `litert-community/gemma-4-E2B-it-litert-lm`.
  Runs via **LiteRT-LM** / the MediaPipe LLM Inference API. Native audio + vision + function
  calling; mixed 2/4/8-bit quantisation.
- Licence: **Apache 2.0** (a change from earlier Gemma generations' custom Gemma Terms of Use —
  confirmed on the model card, `license: apache-2.0`, linking to
  ai.google.dev/gemma/docs/gemma_4_license, plain unmodified Apache 2.0 text). Google still
  layers a separate **Prohibited Use Policy** / intended-use statement on top, referenced from
  that same page — not a blanket "no restrictions," but no longer the old custom licence either.
- The runner-up (**Gemma 4 E4B**, bigger sibling) is an open question, not a decision. Only the
  spike settles which ships.
- The model "doesn't need to be clever — it needs to be obedient and consistent." It is never
  asked to think, only to speak the brief it is handed.

## This dev host (OCI) vs the phone — important

This host is a **Linux dev box**, ideal for:

- Phase 1 Python engine work (object model, state machine, brief-builder, voice loop).
- Running Gemma 4 E2B on desktop (LiteRT-LM, or llama.cpp / Ollama for iteration) to tune the
  *brief* and *prompt* quality — how a small model behaves on the engine's actual output.
- Automated AI playtesting: pointing a **frontier** model at the engine to fuzz it (PRD §14).

**It cannot run the §0 spike.** The spike is specifically about *on-device mobile* performance
under thermal load — time-to-first-token, warm, in a pocket, unplugged, on a real mid-range
Android. A cloud CPU/GPU tells you nothing about that. Keep the two cleanly separate:

- **On this host:** desktop-flattered latency, engine logic, brief quality, model behaviour.
- **On a real phone (separate task):** the go/no-go thermal benchmark. See `spike/README.md`.

Desktop will flatter latency and lull you into false confidence — port to a real phone early.

## What NOT to do

- Don't hand world logic to the AI "because it's easier." That is the failure mode of every
  competitor (PRD §19). Resist it.
- Don't build the phone shell before the engine loop is proven.
- Don't treat the memory-brain experiment (`small-model-big-memory-dev-plan.md`, referenced in
  Gotcha #6/#6a) as settled architecture. It is **exploratory and separate.** The Orb's design
  deliberately keeps continuity in the engine's object model, not in a model memory layer.
- Don't add scope. Prove one room feels alive first (PRD §21).

## Working hygiene (PRD cleanup rule C1, adapted for git)

- **One PRD, one path:** `docs/PRD.md`. The version lives in the file header and in git history /
  tags — *not* in the filename. (This supersedes the old "filename carries the version" rule now
  that the project is in git.)
- Record locked decisions as ADRs in `docs/decisions/`.
- Log everything in experiments — full input/output traces, or you won't know what broke what
  (PRD §14).
