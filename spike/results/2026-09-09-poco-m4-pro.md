# Spike result — `poco-m4-pro` — 2026-09-09

## Device

- **Model:** Poco M4 Pro (5G) — `2201117PG`
- **Chipset:** MediaTek MT6781 (Helio G96)
- **RAM:** 7,924,404 kB total; only ~1,091,996 kB "available" at time of test (the phone was
  under real memory pressure — see Gotchas)
- **Android:** 13
- **Runtime:** llama.cpp, build `1945e0920` (2026-09-09)
- **Model:** `ggml-org/gemma-4-E2B-it-GGUF:Q4_0`, `--jinja --reasoning off --no-mmproj`
- **Backend:** CPU only. **GPU not tested** — no Vulkan/OpenCL backend set up on this box; this
  result covers the pessimistic CPU-only lane, not the full picture the pass mark procedure asks
  for ("run it on CPU and GPU").

## Conditions

- **Unplugged, in-pocket**, ~18.1 minutes of continuous back-to-back inference (small ~1s gaps
  between requests, not idle conversational pacing — chosen to actually generate sustained load
  rather than let the CPU cool between turns).
- 192 requests, rotating through 10 different one-line player utterances against a **real,
  engine-generated brief** (`engine.brief.build_guard_brief` against the v0.1 cell-and-guard
  scenario — not a synthetic prompt), ~350 tokens, pasted below in full.
- Measured over Tailscale from the OCI dev host (`huey`), direct connection (not DERP-relayed).
  Some of each reported "total" time (not TTFT) includes real network latency (~15–65ms observed
  via `tailscale ping`), which is not part of on-device inference cost but is part of what the
  harness measured — noted so it isn't mistaken for pure model latency.

## The brief used

```
You are Garrick, a bored, gruff dungeon guard. A man of few words — one or two short sentences, never more. Never break character, never mention being an AI or a game. Never describe the room or surroundings; that's the Dungeon Master's job, not yours.

# Examples of your voice (style only — not this scene, don't reuse the lines)
```

Sample replies produced during the run: *"I stand my post. They wait. They move."*, *"Halt. Guards. Now."*, *"Business. I have business."*

## Verdict against the pass mark

> A short, in-character guard reply, spoken, beginning within roughly a second, and still doing
> so after twenty minutes, on a warm mid-range phone.

**Split verdict, CPU-only, Q4_0:**

- **Thermal / sustained-use half: passes cleanly.** 192/192 requests succeeded over 18.1 real
  minutes, unplugged, in-pocket. No throttling signature — TTFT and generation speed in the
  second half of the run were flat-to-slightly-better than the first half. Whatever thermal
  headroom this chipset (MT6781) has, it wasn't exhausted at this quant/config in this window.
- **~1-second TTFT half: does not pass, but is close.** Median 1.33s against a ~1s bar, with a
  real 350-token engine-generated brief — this is the first honest reading using a realistic
  prompt rather than a short synthetic one, and it's consistently over the line, not marginal
  noise (only 4.7% of warm requests landed at/under 1s).

**Read this as "close, not there yet, on the pessimistic lane" rather than a hard no:** this is
CPU-only GGUF via Termux with no MTP — explicitly the floor case, not the shipping path
(LiteRT-LM + GPU/NPU + MTP has real headroom above this per the PRD §0 research). Before treating
1.33s as a verdict on the architecture itself, still need: the GPU backend measured, and ideally
the same test against LiteRT-LM rather than llama.cpp/GGUF (the actual shipping runtime).

## Update — 2026-09-13/14: attempted to close out with GGUF tuning, hit a device-specific
llama.cpp/Termux CPU anomaly instead, cross-validated the device is fine via Edge Gallery

Following ADR 0003 (llama.cpp/GGUF is now the chosen shipping runtime), attempted to push this
file's 1.33s median TTFT under the ~1s bar via real on-device tuning (quantisation, thread count,
session/prefix-cache reuse — the same `cache_prompt`+fixed-`id_slot` technique confirmed on desktop
the same day, see `devlog/2026-09-13-engine-onto-llama-cpp.md`). Did not get a clean tuning result;
instead found and diagnosed a real, reproducible device-state problem that makes today's llama.cpp
numbers untrustworthy — worth recording in full since it could resurface.

**What actually happened, step by step:**
1. Reconnected to `poco-m4-pro` via Termux SSH (`~/.ssh/config` host `phone`, port 8022 — separate
   from the wireless-debugging adb path used for the LiteRT-LM work). Confirmed the original
   `ggml-org/gemma-4-E2B-it-GGUF:Q4_0` model and a `llama.cpp` install were still present from
   2026-09-09.
2. First test (fixed `id_slot=0` + `cache_prompt: true`, a real engine-generated brief as system
   message): found a **real bug in the test script**, not the runtime — omitted the system message
   on follow-up turns, which broke character entirely (the model reverted to generic-assistant
   replies, "I am Gemma 4, a Large Language Model...") and made prefix-cache reuse look broken
   (`cache_n≈1`). Fixed by always resending the full brief as the system message every turn
   (matching how `engine/llm.py`'s real `GemmaHarness.ask()` actually works) — confirmed
   **`cache_n=490` out of ~500-509 total tokens on every incremental turn**, a ~96% cache hit rate,
   even better than desktop's ~70%. Replies were correctly in-character once fixed.
3. But per-turn timings were still absurd: even with 490 tokens cached, the ~18 *new* tokens took
   3.3–5.8s to prefill, and turn 0's cold ~500-token prefill took 77–91s (**~6 tok/s** — should be
   50+ on this chipset per the earlier LiteRT-LM CPU numbers on this same device). Device memory was
   critically tight (126MB free, 3.5GB swapped) — a documented gotcha from 2026-09-09 recurring.
4. User closed background apps: memory improved somewhat (1.7GB available) but numbers didn't
   change at all. **Rebooted the phone** (user's suggestion, the right call — a targeted app-close
   wasn't enough): swap dropped to near-zero, but llama.cpp throughput was **unchanged** (still
   ~6 tok/s cold, ~3.5-5.8s per ~18-token incremental prefill). Ruled out memory pressure entirely.
5. Found real corroborating evidence: system-wide `uptime` load average stayed at 15-35 for over
   10 minutes post-reboot (MIUI/HyperOS post-boot housekeeping, invisible to Termux's own `top`,
   which showed 0% CPU / near-zero memory from Termux's own processes) — but this settled on its
   own and, per the next finding, wasn't the actual cause either.
6. **Found a real, confirmed hardware-state anomaly**: `/sys/devices/system/cpu/cpu*/cpufreq/
   scaling_cur_freq` showed the 6 "little" cores locked at **500MHz** (max is 2000MHz) and the 2
   "big" cores at 774MHz (max 2050MHz) — roughly 25-38% of normal clock. Plugging the phone in
   brought the big cores to full 2050MHz, but the little cores stayed at 500MHz regardless.
   Pinning `llama-server` to just the two full-clock big cores (`taskset -c 6,7 --threads 2`) made
   things **worse**, not better (102s cold prefill) — clock speed alone doesn't explain everything.
7. Used `llama-bench` (server-independent, standard methodology) to get a clean reading isolated
   from any of our own HTTP/session-cache code: **~4.0-4.7 pp t/s, ~2.8-2.9 tg t/s**, consistently
   reproduced across the Vulkan backend (auto-selected — confirmed to be `llvmpipe`, the *software*
   fallback we already knew about from the LiteRT-LM investigation, not real Mali GPU), `-ngl 0`
   (forced CPU, no change), and a **fully clean reinstall** (`pkg uninstall llama-cpp-backend-vulkan`,
   `apt autoremove`, fresh `pkg install llama-cpp`, confirmed `backend: CPU` in the output) — same
   ~4.0 pp / ~2.93 tg t/s regardless. This ruled out backend mis-selection, thread count, core
   pinning, and a corrupted install as sole explanations, leaving something real and unresolved in
   this device's current CPU-bound llama.cpp path specifically.
8. **Decisive cross-check, at the user's suggestion**: the user opened Google's own **Edge Gallery**
   app (a LiteRT-LM/MediaPipe LLM Inference API showcase — the *same* underlying runtime this
   file's own header already evaluates, not a different one) running Gemma E2B **on GPU**, on this
   same phone, in this same post-reboot/plugged-in state, and got a real response in **~4 seconds**.
   This is the single fact that resolves the investigation: it's **consistent with, not better
   than**, this project's own already-recorded LiteRT-LM GPU number (mean 3.28s/turn, ADR 0003) —
   confirming that data is trustworthy — and it proves **the device itself is fine**, since a
   GPU-accelerated path on the same hardware, same moment, performs normally. The problem is
   specifically in Termux's CPU-only llama.cpp path today (throttled little cores, and something
   else even the full-clock big cores didn't fix), not the phone as a whole.

**Conclusion:** this file's original 1.33s median TTFT (captured 2026-09-09, when this CPU anomaly
was not present) remains the trusted llama.cpp/CPU number — **not superseded or contradicted** by
today's session, just impossible to reproduce or improve on while this device is in its current
CPU-throttled/anomalous state. ADR 0003 stands unchanged. Not chasing the CPU throttle/anomaly
further today (real time cost, and Termux's sandboxing means llama.cpp on this path can never use
the real GPU anyway — regardless of the throttle's cause, real GPU-class performance for llama.cpp
specifically would need a different deployment path than Termux, which is out of scope here).

**Open thread, new:** why are this phone's little CPU cores locked at 500MHz even while
charging, and why did even full-clock big cores give the same ~4-5 t/s in `llama-bench`? Real,
reproducible, unexplained. Worth a fresh look in a future session with a clear head and more time
— possibly relevant beyond just this benchmark if it affects real background CPU work generally.

## Gotchas from this run

- **Termux got killed outright partway into the first attempt at this run** — not just a network
  freeze, the whole process tree (`tmux` server included) died the moment the phone was pocketed
  and the screen locked, confirmed via `operator(): cleaning up before exit...` in the server log
  and `tmux ls` reporting no server. This happened *despite* Tailscale already being set to
  Unrestricted battery/Autostart from earlier in the session — that fix was necessary but not
  sufficient. Fixed by running `termux-wake-lock` before restarting the server; the retried run
  completed cleanly with 0 hangs. **`termux-wake-lock` should be considered required, not
  optional, for any future hot/pocket run.**
- **`MemAvailable` was only ~1.1GB of 7.9GB total** at test time — plausibly a contributing factor
  to Termux being killed (Android's low-memory killer, on top of or instead of pure Doze/network
  suspension). Worth checking free memory before a future run and closing other apps if it's
  similarly tight.
- This run used `--no-mmproj` (recommended in the earlier session) — RAM headroom from dropping
  the projector may matter more on a phone this memory-constrained than it first appeared.
